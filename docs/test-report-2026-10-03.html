Test & security report · Mercury Schema 1.0.0 release candidate

All 22 schema types tested end to end. One leak found and fixed.

Every schema type was added through the real block editor, checked on the live page as a visitor sees it, and attacked with injection payloads. Access control, request forgery and data leaks were probed for every role. One medium-severity issue turned up: password-protected posts leaked their text through structured data. It was fixed before the 1.0.0 release, with a regression test.

How it was tested

Method

  • Automated suite: 63 unit tests (core logic, no WordPress) and 48 integration tests (REST, rendering, setup, migration) on WordPress 6.0/PHP 8.0 and 7.1/PHP 8.4.
  • Browser: on a test post with a featured image and a two-level category, each type was added from the type picker, every field filled the way a user would, saved, and its status badge and live preview recorded.
  • Live page: a checker fetched the published page as an anonymous visitor and inspected every JSON-LD block: valid JSON, @context, Google's required properties, absolute URLs, and no empty values, HTML or unfilled {{tokens}}.
  • Attacks: script, image and quote payloads in every text field of all 22 types; javascript: links; unknown fields; payloads written straight to the database to bypass the sanitizer; each role against each endpoint; requests without or with forged security tokens; password-protected content.

Test posts, image, categories and users were deleted afterwards, and the site's own settings (only Breadcrumbs enabled, the five site-wide schemas, the plugin list) were restored exactly.

After a schema is applied

What happens next

  1. Saved in one placeThe editor sends the schema to the plugin's API. It checks the user may edit that post, checks field types, strips HTML, enforces size limits, and stores every schema for the post in a single database row. The badge then shows whether it will print, with tokens filled from the post.
  2. Nothing changes for visitorsNo scripts, styles or images are added to the page. The schema is invisible text in the page's code.
  3. Built fresh on every page viewSite-wide schemas are merged with the post's own (a post's schema replaces a site-wide one of the same type). Schemas that are switched off, whose type is off, whose display rules don't match, or whose post is password-locked are skipped. Tokens like {{post_title}} are filled, the result is validated again, and incomplete schemas are held back. Breadcrumbs and navigation are built from the site's structure.
  4. Printed safely in the page headEach schema becomes one <script type="application/ld+json"> tag inside <head>, encoded so no text can close the tag. 22 schemas took 1.4 ms and added 10.4 KB.
  5. Search engines read it on their next crawlGoogle parses the JSON-LD, reports it under Enhancements in Search Console, and may show a rich result. Rich results are never guaranteed and usually take days to weeks to appear after a recrawl.
  6. Stays in syncEdits, token values (a new title or featured image) and deletions apply on the next page view. A page cache, if the site uses one, serves the old version until it refreshes.

Security

Findings

Medium · Fixed

Password-protected posts leaked their text through structured data

On a protected post, schemas using {{post_excerpt}} or {{post_content}} printed the protected text into the page source for visitors who had not entered the password: 14 occurrences on the test post, readable by anyone viewing the source or scraping. Locked posts now skip their own schemas, and site-wide schemas only use public details (title, link, dates). Visitors who enter the password get everything as before.

Fixed in 1.0.0 · regression test added · verified 0 occurrences after the fix
Low · Open

No format check for currency and country codes

Fields such as Product currency, Job Posting salary currency and address country accept any text. Google expects ISO 4217 codes (USD) and ISO 3166 country codes (US), so free text causes warnings in Google's tools. This is a data-quality gap, not a security risk. Recommended fix: a pattern check on those fields.

Not yet fixed
High · Fixed earlier

Editors could reach site-wide routes through URL casing

Found in the previous audit and fixed in an earlier build. Re-tested today: /GLOBAL, /Global and /MERCURY-SCHEMA/V1/global all return 403 for editors.

Still fixed · covered by a regression test

Limits of this audit

Not covered

  • Google's Rich Results Test: it needs a public URL, and the test site is local.
  • WooCommerce product values: WooCommerce was deactivated on the test site, so they were not re-tested today (they passed in the 1.1 testing).
  • The Elementor 3.x fallback menu item: only Elementor 4.3 was available.
  • Multisite networks, browsers other than Chromium, and screen readers.
  • This was an in-house review. An independent security review is advisable before a wide public release.
Next steps

Recommendations

  • Released as 1.0.0. The first public release includes the fix; the download button serves it automatically.
  • Add code checks for currency and country fields.
  • Run Google's Rich Results Test on a staging site with real content before launch.
  • Keep Schema Types in mind: the test site currently has only Breadcrumbs enabled, so other schemas on it show as "Type off" and don't print.
